# ScreenNote user journey repair — 25 October 2026

The prior passing results did not cover the complete range of user experience. In particular, no physical mobile/browser certification was established. This audit starts again at the user interface.

## Confirmed breaks and repairs

- A real desktop Start recording request could remain pending while the app looked unchanged and ignored other actions. Show an explicit browser-permission state with Cancel recording request. Cancellation abandons only that session; a late screen or microphone grant is stopped rather than starting an unexpected capture. Two regression tests cover cancellation during the picker and device-permission stages. The remote browser did not expose a controllable native screen picker, so native capture completion remains unverified.
- Portrait screen source 540×960 had ratio 0.5625 but its desktop preview box measured 832×507 (ratio 1.641). Annotations used the entire letterboxed box, so saved marks could be misplaced. Preview and overlay now share a fitted frame based on actual video dimensions. Recheck: source ratio 0.5625, preview ratio 0.5625, overlay ratio about 0.5621 (integer rounding).
- Import validation rejected otherwise supported device files if the picker supplied blank MIME or application/octet-stream. Supported extensions are now considered only with a matching MP4/WebM container header; browser decoding still must succeed. Tests reject renamed junk, wrong containers and unsupported declared types.
- Live 720×1280 H.264/AAC MP4 imported and played, but actual publication returned 503. The client retried only chunk transfers, leaving reserve/finalization failures to the user. Bounded retries now cover setup and finalization too. A phone-width fixture deliberately fails each stage twice, then reaches the share-link state.
- A transient failed startup health check could disable publishing for the entire visit without a retry control. Health now probes an actual storage read and offers Retry sharing connection. A fixture fails four startup probes, then the retry enables Publish without losing the local clip.
- Local trim/marked-copy AudioContext was created only after metadata/seek awaits. Move creation/resume into the synchronous button action, in line with Web Audio user-gesture requirements, and bound the later resume wait. Regression test proves initialization precedes metadata and cleanup occurs after decode failure. This is a code-level repair, not evidence from a physical iPhone.

MDN reference checked: https://developer.mozilla.org/en-US/docs/Web/API/Web_Audio_API/Best_practices

## User-side evidence

- Production file picker imported the generated six-second 720×1280 H.264/AAC MP4, readyState 4, no decode error. The earlier sample-only evidence was insufficient for portrait files.
- Phone-width UI imported that same real file, accepted an actual pointer-drawn opaque mask and saved a new marked copy. Downloaded WebM: 602,224 bytes, VP8 video 720×1280, Opus audio, six seconds. FFmpeg decoded it; the mask appears in the expected normalized rectangle (approximately x .2–.5, y .205–.4). Lossy encoding produces small colour variations; do not claim exact uniform exported RGB. The original remains separate.
- Waiting-permission Cancel returns to the library and sample import works afterward. Late grants are separately covered by the regression tests.
- Phone-width retry fixtures reach the share state after two reserve and two finalize failures. Failed health probes recover through the visible retry button.
- The attempted local live-backend relay failed in the managed preview environment. Production direct health returned configured true. The relay was removed rather than shipped or represented as production mobile evidence. Responsive UI tests and live production runtime tests are reported separately.

## Evidence limits

No physical Android, iOS, Safari or native screen picker completion is certified here. A CSS viewport is not a physical device. Browser codec availability, native permission UI and mobile backgrounding must not be called universally verified. Storage is an external dependency; the app must preserve a local copy, show a useful failure and permit retry when it is unavailable, rather than promise impossible 100% uptime.

Full current workflow and release results are appended after retesting the deployed changes. Recovery exports contain management capabilities and are never attached to this report.

Stored size is about 1 MB; this is not evidence of which quota was exceeded. Runtime private reads return 403 Forbidden. No secret was retrieved or printed.

No replacement store was created to evade limits and no billing plan was changed. Code cannot restore an account-level suspended allowance. The owner must resolve the storage quota/billing restriction in Vercel before online sharing and shared playback can be accepted. No reset date or price is claimed.

66 automated tests pass, including the added access-denial classification and no-retry test. This does **not** establish a working live sharing journey while storage is suspended.
