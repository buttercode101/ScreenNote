# ScreenNote v0.1.2 — continued hardening

23 October 2026, South Africa.

## Changes

- Capacity recovery on new reservation attempts when the 16-slot store is full. Reclaims abandoned pending uploads or expired/revoked media only after an additional 24-hour grace period, atomically marking records inactive before deleting cloud data. Cleanup failures retain their slots for retry. Active records are preserved. Cleanup is demand-driven, not a scheduled deletion guarantee.
- Missing-metadata orphan slots get a 10-minute observation delay before reuse. Failed metadata creation rolls back its reservation; duplicate in-flight reservations cannot create untracked uploads.
- Recovery-key JSON export/import, scoped to the same origin, with input bounds and duplicate/format validation. Each capability is checked by an owner-authenticated metadata endpoint before local persistence. Recovered management-only records can revoke/delete uploaded videos without a local video file. Existing local videos are retained. Recovery files are private bearer capabilities, not video backups.
- Recording storage failures retain captured bytes in memory with a direct emergency download view. Failure to save recovery chunks no longer aborts otherwise usable in-memory capture. A screen that ends during permission setup is rejected; stopped duration no longer continues advancing.
- Expired share controls consistently use active-link state. Republishing a reclaimed record uses a new identity. Same-file import can be retried after a failed decode.

## Verification before release

32 automated tests pass (previous release: 22). Added coverage includes recovery validation/redaction, authenticated owner metadata, grace periods, cleanup failure, active-slot preservation, orphan recovery, reservation rollback, ended-screen setup and stable recorder stop lifecycle. Storage and media-device tests use simulations.

Production build passes. Browser preview confirms recovery page rendering and invalid-JSON rejection. Production integration and UI results are recorded after execution below.

## Remaining verification boundaries

Native screen-source picker and physical Android/iOS/Safari recording combinations still require device testing. Sharing remains deliberately capped at 16 reservations, five minutes and 25 MB per video. Export recovery keys before losing the original browser; absent a prior export, ownership is not recoverable. Signed playback URLs may persist five minutes after revocation.

## Production verification

- Production Browser: recovery JSON imported through the real file chooser; status reported “Restored 1 recording.” The browser had no local video. Management-only editor showed the upload, disabled local download/rename, and supplied owner revocation/deletion controls.
- Recovery file exported through the actual download button; parsed file keys and origin exactly match the validated synthetic fixture, with no title or video bytes.
- Stop-sharing completed using recovered access in the browser. Server deletion using the recovered capability succeeded; authenticated metadata reported cleanup complete and viewer access returned 404.
- Owner status refresh reconciles changes from another browser, and blocks navigation during its request to preserve the selected recording identity.
- Recovery page: eight overflow checks pass at 360, 390, 480, 768, 834, 1024, 1440 and 1920 CSS pixel iframe widths. Local sample import and editor still work after recovery UI changes.
- Invalid recovery JSON fails visibly without server mutation.
- Native permission-picker and physical-device combinations remain unverified. Capacity-pressure cleanup is covered by injected-store tests; no real user uploads were expired or deleted to pressure-test production capacity. Only the synthetic test upload was removed.
